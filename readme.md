## `01` — PROFILE

I'm an **Information Technology student and aspiring Software Engineer** with a strong interest in the engineering behind reliable software systems.

My current work revolves around **Data Structures & Algorithms, C++, Python, Linux, backend engineering, infrastructure, and distributed systems**.

I prefer learning through implementation. Rather than stopping after understanding a concept theoretically, I try to turn it into something executable, test it, break it, debug it, and understand what actually happened.

I'm especially interested in the layers that sit underneath modern applications:

**memory · processes · operating systems · networking · databases · APIs · concurrency · infrastructure · distributed systems**

I'm currently building **GriefOS**, an AI-powered platform intended to help families navigate practical processes following bereavement, while also exploring systems programming through projects such as a **multi-client TCP chat server**.

My long-term objective is to become a **systems-oriented software engineer capable of designing, implementing, debugging and scaling reliable software for large-scale environments.**

# `07` — ENGINEERING PHILOSOPHY

<div align="center">

> **Don't just make it work. Understand why it works.**

</div>

I believe the best way to learn engineering is to repeatedly move between **theory and implementation**.

I want to be comfortable with the uncomfortable parts of development:

reading unfamiliar code, investigating errors, understanding logs, tracing network requests, finding bugs, questioning assumptions and figuring out why a system behaves differently from what I expected.

I also don't want lack of mastery to become a reason to avoid building.

**Learn enough to start → build → encounter problems → investigate → improve.**

That cycle is where most of my learning happens.

# `10` — BEYOND THE CODE

I'm particularly interested in engineering problems where software has to work under real constraints.

That includes questions such as:

- How should a service behave when another service is unavailable?
- How do we design APIs that remain maintainable as they grow?
- How should data be stored and indexed?
- What happens when thousands of requests arrive simultaneously?
- How do we diagnose a production failure?
- How do we make a service observable?
- How do systems recover from partial failures?
- How can infrastructure be automated reliably?
- How do distributed systems maintain useful guarantees despite failures?

These are the kinds of problems I want to gradually become capable of solving.
